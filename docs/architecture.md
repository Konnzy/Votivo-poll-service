# Layered architecture та межі лабораторної №4

## Шари

1. Presentation: `controller` та `dto`. HTTP, Bean Validation, коди відповіді.
2. Business: `service`. Права власника, перевірка стану, повнота публікації, транзакції.
3. Persistence: `repository` та JPA-відображення у `model`. SQL виконується через Spring Data JPA.

Сервісний шар отримує поточного користувача через `CurrentUserProvider`; клієнт не задає власника.
Контролери залежать лише від сервісу, репозиторії не залежать від HTTP. DTO відокремлені від JPA-сутностей.
У базовій версії JPA-сутності одночасно є предметною моделлю; окремі дублікати domain/entity не вводяться.
`PollMapper` виконує перетворення, `PollAccessService` перевіряє власника,
`PollValidationService` перевіряє стан і готовність до публікації. Репозиторій є абстракцією доступу до БД.

## Модель і правила

`Poll` містить впорядковані `Question`, кожне питання містить впорядковані `AnswerOption`.
Дочірні сутності зберігаються каскадно. Чернетка замінюється повністю, тому ID питань і варіантів
при PUT можуть змінитися. Після публікації зміна вмісту заборонена, ID стають стабільними.

Життєвий цикл: `DRAFT → PUBLISHED → CLOSED → ARCHIVED`. Зворотних переходів немає.
`blocked` є окремою ознакою модерації. Заблоковану чернетку не можна змінити чи опублікувати;
власник може закрити/архівувати вже опубліковане заблоковане опитування.
Адміністратор може переглядати та блокувати, але не редагувати чуже опитування.

Публічний каталог показує лише `PUBLIC + PUBLISHED + !blocked`.
Прямий публічний доступ зберігається для CLOSED/ARCHIVED. LINK вимагає випадковий UUID share token;
звичайного ID недостатньо. Власник та адміністратор можуть читати чернетки й заблоковані опитування за ID.
Неавторизований користувач може лише читати дозволені опитування. Анонімність відповіді не означає
участь без автентифікації: правила участі належать Vote Service.

`@Version` виявляє одночасні зміни одного Poll; конфлікт повертається як 409.
`open-in-view=false`, DTO формуються всередині сервісної транзакції.
Міграції Flyway є джерелом схеми, Hibernate лише перевіряє її.
Застосунок та тести використовують JVM timezone UTC, незалежно від застарілих системних timezone aliases;
дати API зберігаються як Instant, колонки БД мають тип TIMESTAMP WITH TIME ZONE.

## Рішення за суперечностями матеріалів

- №1 задає RPC/Protocol Buffers між сервісами, №2 описує REST та RabbitMQ.
  Цей PR реалізує лише зовнішній REST/JSON. Синхронний протокол між сервісами залишається відкритим;
  gRPC/REST-клієнт без погодженого контракту не додається.
- FR-7 визначає PUBLIC і доступ за посиланням. Приватні запрошення не реалізуються.
- Публікація вважається початком голосування; редагування припиняється одразу після публікації.
- Мінімум 1 питання та 2 варіанти перед публікацією є рішенням цієї реалізації, а не цитатою FR.
- Часовий розклад на Use Case Diagram не деталізований у FR і відкладений.
- Зміна/скасування голосу потребує уточнення FR-11 з командою Vote Service.

## Наступні інтеграційні контракти (пропозиції)

- Poll → Vote: достовірний запит про наявність голосів і координація видалення, яка виключає
  одночасне приймання голосу та видалення опитування. Простого асинхронного лічильника недостатньо.
- Vote → Poll: доступність, blocked/status, питання, ID варіантів, SINGLE/MULTIPLE та anonymous.
  Внутрішній API має автентифікувати сервіс і не повинен повертати share token у загальні списки.
- Poll → RabbitMQ → Vote/Result: `PollPublished`, `PollClosed`, `PollBlocked`.
  До ввімкнення потрібні версійована схема подій, eventId, pollId, revision, ідемпотентні споживачі
  та transactional outbox для узгодженості з транзакцією БД.
- Закриття/блокування повинні гарантовано припиняти приймання нових голосів у Vote Service;
  політика узгодженості та обробка запитів у польоті погоджуються окремо.

Зараз немає зовнішнього RPC, RabbitMQ producer, outbox або прихованого fallback, який повертає
«голосів немає». Ці можливості не позначаються як завершені.
